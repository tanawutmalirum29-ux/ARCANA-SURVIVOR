## Corrective architecture

`src/integration/eventExclusiveWriter.js` uses a single **IndexedDB readwrite transaction** on database `arcana-survivor-event-v2-transactional`, object store `event-snapshots`, record key `v2`. Each call opens one transaction, reads the previously committed record inside it, executes the existing **synchronous** `commitStoredEventTransition` reducer/validator against a staged in-memory snapshot, then enqueues **one** IDB `put` inside the same active transaction. Result `COMMITTED` is returned **only** when the real IDB transaction fires `oncomplete`; errors, blocked storage, aborted writes and power-loss injection fail closed. Independent competing same-origin tabs' overlapping IDB `readwrite` transactions on the same store are serialized by the browser transaction manager; no reliance on delayed `localStorage` cross-tab visibility, no browser Web Locks, no timing sleeps, no uncontrolled fallback.

The default `allowInitialize=false` rejects an empty new IDB record with `MIGRATION_REQUIRED`, rather than silently losing old `localStorage` Events v2 replay/claim ledgers. Explicit initialization is **only for known-fresh test profiles** and must not be enabled in a production profile until a separately QA-reviewed migration plan can prove that no historical history is lost. The legacy `arcana-survivor-events-v2` localStorage key and normal player profile are not read, written or removed by this module. The original unguarded helper and standalone localStorage adapter remain dormant; they are **unsafe for cross-tab updates** and are NOT connected to game runtime.

A database transaction is not an authoritative payment or wallet system. This prototype does not create server entitlement rights, coordinate multiple devices, secure clock/season cutoffs, atomically update an independent wallet with the Events outbox, or defend against malicious scripts. A future launch must place every Events state mutation and pending grant ACK through a single approved transaction/authority, migrate existing data safely and provide a server-side payment/authentication plan where relevant. If IDB is unavailable or blocked, the system stops instead of using localStorage.
