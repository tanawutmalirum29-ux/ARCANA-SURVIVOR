# ENGINEER-MIGRATION #48 — dormant Events legacy → IndexedDB contract

Status: **DESIGN / NEGATIVE TESTS ONLY; CUTOVER AND RUNTIME HOLD**. No production module, feature flag, wallet, Economy catalog or existing user save is modified by this PR. The separate profile/Gold wallet key is **not** an Events migration source.

## Verified source and destination (main `bef57421bde4f2f5f4396fee9a5140c4379abec1`)

- Source: `localStorage['arcana-survivor-events-v2']` through `src/integration/eventLocalStorage.js`. Despite the key name, value may have `schemaVersion: 1` or `2`. Missing key means `getItem() === null` **only**; parse failure, denied storage, undefined and JSON null mean error, never a new save.
- Legacy v1: `{schemaVersion:1,progress,claims,tokens,purchases}`. The pure `migrateEventStateV1` gathers deduped `progress[*].seen` into `seenEventIds` and adds `mintedTokens:{}` for *some syntactically acceptable* ledgers. It **does not certify full claim/intent identity, ACK flags, progress structure, key uniqueness or historical authenticity**. Existing `claims[*].intent.idempotencyKey` and `delivered:false` outbox must be preserved, but they first require **separate validation and provenance attestation**; a clean-looking v1 is not independently enough to approve cutover.
- Valid v2: `{schemaVersion:2,progress,claims,tokens,purchases,seenEventIds,mintedTokens}`. Global replay IDs, token minted/balance/spend conservation, pending claim/purchase intents and ACK flags are indivisible historical data.
- Destination: IndexedDB `arcana-survivor-event-v2-transactional`, object store `event-snapshots`, record `v2`, via `src/integration/eventExclusiveWriter.js`. A `readwrite` transaction serializes origin tabs and reports COMMITTED only after `oncomplete`.
- **No legacy → IDB copy API exists in main.** `commitExclusiveEventTransition` defaults `allowInitialize=false` and returns `MIGRATION_REQUIRED` on absent IDB. Enabling `allowInitialize:true` is **not migration**: it would start a fresh Events history. Do not enable it for existing users. Standalone localStorage writer has no cross-tab serialization.

## Proposed cutover algorithm — requires separate CEO production API approval

1. **Freeze/fence all legacy Events writers and ACKs, including every already-open tab and background worker.** CEO must document verifiable evidence that every possible writer/ACK path has stopped and will reject post-cutover legacy writes (e.g. enforceable generation/lease admission controlled by the same authoritative writer), not merely send a BroadcastChannel notice or listen to `storage` events. An already-running legacy script that cannot observe the new fence may keep writing; **absence of evidence of such tabs is NOT proof of quiescence**. With the existing unfenced localStorage adapter, full cutover is **HOLD**. No timer, Web Locks plus stale localStorage, or UI-click-based fence can justify a race-free switch. Current runtime remains unmounted/dormant.
2. On same origin, read dedicated legacy key with strict absence and JSON semantics, retain exact source bytes and schema/version. Distinguish missing, corrupt, unsupported, permission denied and transient failures. A missing legacy key is not sufficient to initialize IDB without explicit attestation of a genuinely fresh profile.
3. **Strictly attest legacy origin before any copy.** Existing `stateCopy` / `listPendingEventGrantIntents` / `migrateEventStateV1` check only a subset of invariants; **they are NOT an authoritative full receipt validator**. A **separate new CEO-approved typed validator/attestation API** must first validate complete source shape and cross-record constraints, reject missing/unknown fields relevant to safety, verify frozen catalog/definition/revision provenance, and prove the required history is complete. Verify at minimum:
   - Each `progress[period]` has a period/key consistent with its event ID, version/revision and authenticated frozen definition, legal time bounds (`from`, `end`, `claimUntil`), nonnegative counters, complete `objectives` and valid `seen` replay IDs; global replay membership and period history must be consistent. **Missing period/progress with an existing claim or purchase is `INCOMPLETE_PROGRESS`**, not an empty history.
   - Each `claims[rewardId]` corresponds to exactly one earned objective in that period. Validate receipt ID, claim timestamp/window, `kind`, complete typed `intent` fields, `rewardType`, `amount` and `sourceRef` against the frozen earned reward. For externally delivered intent, require the stable `idempotencyKey === 'arcana:demo:' + rewardId`; require `delivered` to be explicit boolean, never default missing/undefined to false or true. Each `purchases[receiptId]` must meet equivalent validated reward/offer, cost and token-history constraints. **Enforce unique stable idempotency keys across BOTH claims and purchases**, including conflicting delivered/pending rows. Unknown type, missing key, mismatch/duplicate, malformed amount or receipt => `MIGRATION_INVALID_RECEIPT`; no wallet grant/ACK.
   - Validate v2's replay and cumulative `mintedTokens` / balance / spend conservation *in addition* to receipt validation; v1 `migrateEventStateV1` may be used **only after** the separate verifier approves its source and historical completeness. Explicit token purchases, token claims, positive balances, unknown mint/spend history, or previously pruned token/replay records mean `LEGACY_TOKEN_HISTORY_UNKNOWN` / `LEGACY_PROVENANCE_UNKNOWN` HOLD. **A zero token balance does not establish zero historic spending or claims.** Do not invent lost replay IDs or reconstruct tokens.
   - Since this is untrusted client-controlled localStorage, no syntactic validator, catalog cross-check or SHA/checksum can establish that older progress/claims were not forged, silently pruned or awarded on another device. A checksum only proves byte equality; **without separately trustworthy history provenance/attestation, return `LEGACY_PROVENANCE_UNKNOWN` and keep runtime/rewards disabled even for well-shaped data**. This stage does not authorize importing claims into a live economy.
4. Inside **one** IDB readwrite transaction, read destination `v2`. If already populated, verify a durable migration provenance marker and full snapshot equality or a later authorized transaction lineage; otherwise `MIGRATION_CONFLICT` HOLD. Never overwrite an existing IDB ledger from a stale localStorage copy. If empty and the fenced/validated source is eligible, atomically put the complete v2 snapshot **and** a migration receipt (source checksum/schema/version, destination identity, completed marker) in the same store/transaction. No `COMMITTED` before `oncomplete`; abort leaves destination unchanged.
5. Verify committed IDB snapshot + receipt in a fresh read transaction and check that no legacy writer advanced after the freeze. If the process crashes before commit, retry from preserved source; if after commit but before verification, compare/verify existing IDB and return `ALREADY_MIGRATED` without recopy or grant. **Keep legacy bytes untouched** at all stages; any future deletion/retirement needs its own approved backup/rollback gate.
6. After an explicit authority switch, **all** Events progress, Claim, Token spend, pending outbox mutations and outbox ACKs must use the same IDB transactional authority. Never fall back to legacy localStorage; reject writes from stale tabs. IDB protects Events only, not the separate wallet transaction.
7. Wallet delivery remains OFF. Any future earned-only coordinator must persist the Events pending intent first, durably persist an idempotent wallet grant with the same key, **then** persist IDB outbox ACK. Crash after wallet write/before ACK must replay to ALREADY_APPLIED and ACK once without double grant. SEASON_XP/EVENT_TOKEN are not wallet payments; premium/real-money entitlements are excluded.

## Known unsafe acceptances in existing unchanged validator (independent QA #26)

QA reviewed exact original PR #49 HEAD `c8f80da74792be68144177813e5c0c86ededb96c` and executed 7 isolated synthetic legacy fixtures against the real current reducer: control + **six malformed fixtures were all accepted** by `migrateEventStateV1` and `prepareStoredEventState`. This means existing validation **must not** be cited as migration certification. Accepted bad inputs included: (1) missing pending `intent.idempotencyKey`; (2) arbitrary idempotency key with GOLD amount 999999 instead of the earned 25; (3) missing boolean `delivered`; (4) absent `objectives`; (5) absent `claimUntil` and `definition`; (6) a pending claim remaining after `progress` was wiped. QA evidence: https://github.com/tanawutmalirum29-ux/ARCANA-SURVIVOR/pull/49#pullrequestreview-5600500681. These flaws precede this test-only PR; they are not a claim that its tests corrupted user data.

**Status of strict validation tests:** explicit `test.todo` entries in `legacySafety.test.js` encode the missing hard-denial behavior without falsely showing PASS. No strict legacy validator, attestation source, atomic snapshot+receipt copy, stale-tab fencing or real wallet/ACK authority is implemented. Passing existing tests is compatible with a **HOLD**, not permission to activate or merge as a fully safe migration.
